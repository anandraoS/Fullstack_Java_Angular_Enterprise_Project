# API contracts and backward-compatibility guide

Decision record: [ADR-0007](../adr/0007-api-versioning.md). Normative endpoint list: [shared contract](00-shared-contract.md) section 5.

## 1. Contract overview

* Base path `/api/v1`, through the gateway on port 18080 locally. Each service also serves its own OpenAPI document at `/v3/api-docs`; committed exports belong in `specs/openapi/<service>.json` (order, inventory, fulfillment, notification).
* Errors are RFC 7807 `application/problem+json` with a stable UPPER_SNAKE `code` (the `code`, not the `title` or `detail`, is the machine contract).
* Pagination envelope `{content, page, size, totalElements, totalPages}`; invalid paging or sort fields are a 400, never clamped.
* Required headers: `Idempotency-Key` on `POST /orders`; `X-Correlation-Id` accepted and echoed.
* Response-only headers clients may rely on: `Location`, `Idempotent-Replay`, `X-Correlation-Id`, `Retry-After` (429), `Deprecation`, `Sunset`.

## 2. Rules inside v1: additive only

Allowed without a new major version:

1. Add an optional request field with a safe default.
2. Add a response field.
3. Add a new endpoint, a new optional query parameter, a new response header.
4. Add a new error `code` (clients must treat unknown codes as generic by status).
5. Loosen validation (accept more).
6. Add a new enum value only for enums documented as open (`channel`, `tier`, error `code`). Order and saga status enums are documented as closed per major version except by announced release note, and the UI renders unknown statuses with a neutral chip.

Clients MUST ignore unknown response fields (the Angular models in `frontend/oms-ui/src/app/core/models.ts` only read what they use) and MUST NOT rely on field order.

## 3. Breaking vs non-breaking

| Change | Breaking? | Handling |
|---|---|---|
| New optional request field | No | Document default |
| New required request field | Yes | Make optional with default, or new version |
| New response field | No | Additive |
| Remove or rename response field | Yes | Add new field, deprecate old, remove in v2 |
| Change field type, scale or units (money scale 2, ISO dates) | Yes | New field or v2 |
| Change meaning of an existing value | Yes | v2 |
| Tighten validation (smaller max, new pattern) | Yes | v2, or warn first via `Deprecation` |
| Loosen validation | No | |
| New endpoint | No | |
| Remove endpoint or change method/path | Yes | Deprecate with `Sunset`, remove in v2 |
| New HTTP status for an existing failure | Usually yes | Treat as breaking unless documented as extensible |
| New error `code` | No | Clients fall back on status |
| Change default page size or max | Yes | Announce, version |
| New role required for an endpoint | Yes | Announce; security fixes may override with notice |
| Change authorization from 403 to 404 (or reverse) | Yes | |
| Rate limit tightening | Operationally breaking | Announce |

## 4. Deprecation process

1. Mark in OpenAPI (`deprecated: true`) and the release notes.
2. Start returning `Deprecation: true` (or an HTTP date) and, once the removal date is fixed, `Sunset: <HTTP-date>` plus `Link: <docs-url>; rel="deprecation"`. The gateway can add these per route without service changes.
3. Minimum notice: 90 days for external clients; shorter only with the UI as sole consumer and a coordinated release.
4. Track usage by route and client in gateway metrics; remove only when traffic is zero or the sunset date passes.
5. Remove in the next major (`/api/v2`), keeping v1 routed in the gateway until its own sunset.

## 5. Enforcement

* Contract tests: each service's tests assert status, headers and JSON shape of the documented examples (validation envelope, problem+json, paging, Idempotency-Key behaviour). The UI keeps its models aligned with section 5.5 of the contract.
* OpenAPI diff in CI: generate the spec from the running service, diff against the committed `specs/openapi/<service>.json` with an OpenAPI diff tool, and fail the build on breaking changes; intentional breaking change requires bumping the major path. Non-breaking diffs require the updated export to be committed in the same PR.
* Review checklist for any controller change: new fields optional? defaults documented? error codes listed? example added to `tests/api-collection`?
* Status (2026-10-18): the committed exports exist: `specs/openapi/{order,inventory,fulfillment,notification}-service.json` (exported from the running services' `/v3/api-docs`) and `specs/openapi/api-gateway.json` (generated by `scripts/gen-gateway-openapi.mjs`, not exported). `node scripts/export-openapi.mjs --check` reports no drift on the final stack. The CI diff step is not wired into `ci.yml` (open). `tests/api-collection/` (Postman collection, environment template, `oms.http`) exists; the collection was run by a Node interpreter only, never in Postman or newman.

## 6. Introducing v2 (procedure)

1. Add controllers under a `/api/v2` mapping in the owning service; keep v1 controllers untouched, mapping both to the same domain services.
2. Add a gateway route for `/api/v2/**` next to the v1 route.
3. Export `specs/openapi/<service>-v2.json`; keep v1 export frozen.
4. Announce deprecation of v1 per section 4.

Events are versioned separately: see [event-schema-evolution.md](event-schema-evolution.md).
